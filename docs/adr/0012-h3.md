# ADR-0012: h3, pinned exactly, for the title shards' base cells

Status: proposed · 2026-11-20 · Phase 1 (task 11) · Spine: none

## Context: the requirement or measurement that forces a decision (link the metric/ledger entry)

The data plane splits each interval's titles by H3 resolution-0 cell (`docs/design/p1.md` §6.4;
plan §10, Phase 1 task 11): one title shard per base cell with coverage, so the Lens fetches only
the cells its cap touches. The point shard stores each point's base cell in a `cell` column
(§6.3), set by the publisher, so that the browser needs no H3 library and the page and the
publisher can never put a point near a cell edge in two different cells.

So the publisher has to know, for any latitude and longitude, which of H3's 122 base cells
holds it. The later phases need H3 at finer resolutions in the same process family: resolution
4 for the attention hours (P2), 3 for severity cells, 8 for population (P3).

No metric forces the choice, so there is no ledger entry.

## Prior: what you expect each option to measure, before measuring (bake-offs and triggers)

There was no bake-off: the plan names H3. No prior was written down before the work, so none
is claimed.

## Options considered: each with cost, risk, ops burden, and the trigger that would change the answer

| Option | Why, or why not |
|---|---|
| `h3`, the Python bindings of the H3 C library | **Chosen.** The reference implementation, Apache-2.0, maintained with the C library, no Python dependencies, wheels for every platform we build on. It covers every resolution the later phases need |
| Our own resolution-0 code | Locating a base cell needs H3's icosahedron faces, its face-to-IJK projection and its lookup tables, copied from the C library. A few hundred lines and tables to get exactly right, to be thrown away when P2 needs resolution 4 |
| A latitude-longitude grid instead of H3 | No dependency, but every later phase is keyed by H3 cells; the title shards would be the one place that is not |
| DuckDB's H3 extension | A community extension of a large package the publisher does not otherwise use |

Trigger to revisit: if the publisher moves off Python, or if the H3 bindings stop shipping
wheels for linux/arm64.

## Decision: exactly one choice

Add `h3==4.5.0` as a dependency of `globalens-worker`, pinned exactly. It was released on
2026-05-30, well outside ADR-0001's cooldown, and brings no other package. `uv.lock` lists
wheels for CPython 3.13 on macOS arm64 and on Linux x86-64 and aarch64.

`apps/worker/src/worker/cells.py` is the only module that imports it, and it exposes one
function: `base_cell(lat, lon) -> int`, a number from 0 to 121, checked to be in that range.

## Evidence: bench/eval/bake-off links; pre-registration; prior vs measured

Run on the owner's Mac (Apple M3 Pro) on 2026-11-20 UTC:

- `apps/worker/tests/unit/test_cells.py`: the centre of every one of the 122 base cells maps
  back to that cell, so every number from 0 to 121 occurs; the poles and the antimeridian have
  cells; and for random points (Hypothesis) the answer is in range and the same every time.
- The shard tests check that every point's `cell` is the cell its title is filed under, and that
  more cells than the write budget allows share one title object.
- The publisher's runs (the local run against live GDELT and the replay of a fixture day) wrote
  title shards by base cell; their sizes and counts per interval are in `metrics/ledger.jsonl`.

**Not verified: that linux/amd64 and linux/arm64 give the same cell for every point.** H3 does
floating-point geometry, and a point that sits on a cell edge to the last bit could fall on
either side on two machines. That changes nothing for correctness (the publisher stores the cell
it computed, and the page reads it), but a shard built on two machines could differ and get two
keys. It is checked with ADR-0010's cross-architecture check, before both nodes publish (P2).

## Consequences: what gets easier/harder; rollback plan; what we will measure next

**Easier.** The title shards are keyed the way the rest of the plan is, and P2's resolution-4
cells need no new dependency.

**Harder.** One more compiled extension in the worker image (task 7). The package ships no type
information, so `cells.py` turns off four of pyright's unknown-type checks for itself; what goes
in and what comes out are typed.

**Rollback.** Replace `cells.py`. A different partition would change the `cell` values, and so
every title shard's key: a new layout, published from the next pass on, with nothing to migrate
(the live objects expire after 48 hours).

**Next.** The cross-architecture check above.
